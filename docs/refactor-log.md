## P0. 데이터 복구

**문제**: 로컬의 `faiss_index_cpu.index`(47,730 벡터)와 `metadata_list.pkl`(195,787행)이 짝이 아니었다.
`data_process.ipynb`를 대조한 결과, 인덱스는 리뷰만 임베딩한 초기 실험(셀 39~41), 메타데이터는 최종본(셀 32~33)이었다. 진짜 인덱스는 유실.

**설계**
- 원본 CSV는 불필요 — pkl의 `text_for_embedding`이 임베딩 직전 최종 입력임을 195,787행 전수 재구성으로 확인.
- `scripts/reembed.py`: 노트북 레시피(bge-m3-korean, max_len 512, 비정규화, `IndexFlatL2`) 재현.
  - 한 번의 forward로 **CLS·Mean 두 인덱스**를 동시 생성 (추가 비용 ≈ 0).
  - 길이순 정렬 배치로 패딩 낭비 감소, 3,200건 단위 shard 원자 저장 → 중단 후 재개 가능.
- 결과: MPS에서 약 60분(원본 Colab T4 2시간 34분).

**발견**: 노트북은 문서를 **CLS 풀링**으로, 앱의 `HuggingFaceEmbeddings`는 쿼리를 **Mean 풀링**으로 임베딩 → 같은 텍스트 코사인 0.86~0.88.

## P1. 베이스라인 평가 체계 (`baseline-v0` 태그)

**원칙**
1. 버그를 고치기 **전에** 측정한다 — 고친 뒤에는 before 점수가 사라진다.
2. 기존 `src/` 로직은 한 줄도 바꾸지 않는다. 인프라(LLM 생성, Maps 클라이언트)만 교체.
3. before/after는 **같은 모델**로 잰다. 비교 대상은 모델이 아니라 로직.

**평가 3층**
| 층 | 무엇을 | 채점 |
|---|---|---|
| A. 검색 컴포넌트 | 골든 쿼리 73개 → Top-5의 지역·카테고리 | 메타데이터로 자동 (라벨링 0) |
| B. E2E | 여행 요청 20개 → 완성 일정 | 슬롯·카테고리·지역·중복·타임라인 자동 |
| C. 취향 적합도 | 일정의 장소가 취향에 맞는가 | LLM-as-judge(리뷰 근거) + 수기 라벨 kappa 검증 |

정답이 정해진 항목까지 judge에 맡기지 않은 이유: 자동 채점이 가능한 걸 LLM에 물으면 비용·편향만 늘고 "왜 정답이 있는데 LLM에 물었나"에 답할 수 없다.

**골든셋 설계**: 동명 시군구(중구·강서구·고성군) 29, 광주광역시 vs 경기도 광주시 6, 일반 30, 지명 쿼리(해운대 맛집 등) 8. 약점을 겨냥해 의도적으로 구성.

**인프라 교체**
- `src/llm_factory.make_llm` → `init_chat_model(LLM_MODEL)`. gpt-5 계열은 temperature 미지원이라 분기.
- `src/maps_compat.RoutesCompatClient`: 신규 GCP 프로젝트는 legacy Directions/Distance Matrix를 켤 수 없어 **Routes API로 legacy 반환 형태를 재현**. 디스크 캐시, 네트워크 오류는 캐시하지 않음(리뷰 I1).

**모델 결정 과정**
- OpenAI: 교육장 공용 키라 사용하지 않기로 결정.
- `qwen3:8b`: **도구를 한 번도 호출하지 않고 가짜 장소로 일정을 지어냄** — 실패처럼 보이지 않는 가장 위험한 유형.
- `qwen2.5:7b-instruct`(채택): 도구 호출 형식은 정확하나 옛 에이전트 루프에서 날씨 도구 무한 호출 발생.

**정의 변경 기록**
- 성공 = 예외 없음 **+ 장소 ≥ 1** (빈 일정·오류 분리). 품질 지표는 성공 건 평균, 비용은 실패 포함 평균 병기.
- 이동 시간은 타임라인이 계산된 일정만 (없으면 0이 아니라 None) → `has_timeline` 지표 추가.

**베이스라인 결과 (qwen2.5-7B)**
| 지표 | 값 |
|---|---|
| 검색 지역 정확도@5 (전체 / 광주 / 지명) | 0.85 / 0.63 / 0.45 |
| E2E 성공률 / 무한 루프 / 빈 일정 | 0.45 / 0.45 / 0.10 |
| 타임라인 완성률 (성공 건) | 0.11 |
| 여행당 LLM 호출 (실패 포함) | 23.9 |
| judge 취향 적합도 | 2.21 / 5 (자기 채점, 수기 검증 대기) |

**환경 이슈**: macOS에서 torch와 faiss가 각자 libomp를 로드해 병렬 검색 스레드에서 세그폴트 → `OMP_NUM_THREADS=1`. **이 설정이 CPU 임베딩을 1스레드로 묶어 베이스라인 지연을 부풀렸을 가능성** — 재측정 필요(아래 미결).

## P2. 버그 수정 (건별 재측정)

**측정 방법**: 베이스라인 때 저장된 LLM 캐시를 그대로 쓰면 지역 해석·멀티쿼리 LLM 출력이 동일 → 점수 변화 = 순수 코드 수정 효과. Ollama 호출도 없어 가볍다.

### P2-0. 검색 단계 분리 (리팩토링)
- `find_and_select_best_place`에서 `retrieve_candidates()` 추출. 평가 어댑터가 복제본 대신 실제 함수를 호출.
- 검증: 73/73 항목 top-k 완전 동일.

### P2-1. 지역 필터 (광주·동명 구)
- **원인**: `_filter_candidates`가 접미사(시·군·구·광역시)를 떼고 부분 문자열 비교 → "광주광역시"와 "경기도 광주시"가 둘 다 "광주", "부산 강서구"가 "서울 강서구"를 통과.
- **설계**: 이미 있던 `src/region_cut_fuzz.REGION_STRUCTURE`(행정구역 표)를 재사용해 `(시도, 시군구)`로 정규화 후 비교하는 `region_matches`. "경기 광주"→광주시, "강원 고성"→고성군처럼 표에서 접미사 복원.
- **1차 시도의 회귀**: LLM이 "전북도", "경북도" 같은 비표준 약칭을 내놓아 결과가 비었다(옛 코드는 우연히 통과) → "도" 제거 후 별칭 재조회로 보완.
- **결과**: 지역 정확도@5 0.85 → **0.92**, 광주 0.63 → **1.00**, 동명 0.89 → 0.97, 빈 결과 0.03 → 0.01. 회귀 없음.

### P2-2. 풀링 불일치 (잠정)
- 문서 원문으로 자기 자신을 검색한 거리: CLS 인덱스 229.9 → Mean 인덱스 < 0.001.
- **그러나 지역 지표는 중립**(0.92→0.90, 지명 n=8에서 0.55→0.40). 지역 정확도는 P2-1 이후 필터가 결정하므로 풀링 효과를 못 본다.
- "풀링을 맞췄더니 좋아졌다"는 **현재 데이터로 주장할 수 없음** → 관련도 지표로 판정(A안): 취향 쿼리 60개 × Top-3을 judge로 채점, CLS vs Mean 비교. `INDEX_DIR`로 전환 가능하게 두고 판정 대기.

### P2-3. 중복 제거 키
- 장소명만으로 합치면 다른 지역의 동명 가게가 사라짐 → `(장소명, 지역)`.

### P2-4. 기타
- `exclude_places=[]` 가변 기본값 → `None`.
- 근거 리뷰 추출이 **항상 빈 리스트**였음(한 줄 포맷의 `page_content`를 줄 단위로 탐색) → 메타데이터 `리뷰` 사용.
- `config.py` 파일 전체가 두 번 반복돼 LLM·Maps 클라이언트가 두 번 생성되던 문제 제거(실제 적용되던 두 번째 정의 유지).
- PDF tool 여분 인자: LangChain이 무시하므로 버그 아님 → 제외.

### P2-5. 임베딩 디바이스 (정정 이력)
- MPS 0.17초 vs CPU 4.3~10.9초를 보고 기본값을 가속기로 바꿨으나, **서비스 배포 대상이 CPU인 의도된 설계**라 되돌림. `EMBED_DEVICE`로 개발·평가 시에만 가속기.
- 4.3~10.9초는 **다른 파이프라인·Ollama와 경합 중, OMP 1스레드 상태**에서 잰 오염된 값. 한가한 상태에서 재측정 예정.
- CPU 유지 전제의 개선 후보: 멀티쿼리 **배치 임베딩**(3회 → 1회), 쿼리 임베딩 캐시, ONNX/int8 양자화.

### P2-6. tool 모듈 분리
- 620줄 `src/tools.py` → `chains / geo / retrieval / place_tools / itinerary_tools / weather`.
- 본문 이동만. **LLM에 노출되는 tool 정의 7개(이름·설명·JSON 스키마)가 분리 전후 동일**함을 검증 — 정의가 바뀌면 에이전트 동작이 바뀌므로.
- tool 입출력 구조화(Pydantic `args_schema`, envelope)와 초안 생성의 워크플로우 전환은 P3.

## 서비스 관점 지표 (P2에서 계측 추가)

| 분류 | 지표 | 이유 |
|---|---|---|
| 작업 성공 | 성공률 / 빈 일정률 / 오류(루프)율 | 에이전트의 1차 KPI |
| 지연 | 요청 p50·p95, **분해: LLM·벡터검색·Maps·기타** | 병목을 숫자로 찾기 위해 |
| 도구 사용 | tool 오류율, soft 실패("추천 장소 없음" 등 문자열 실패), **무효 tool call률**(파싱 실패·없는 도구), 중복 호출 수 | 에이전트 신뢰성의 핵심 |
| 효율 | 요청당 LLM 호출·토큰 (실패 포함) | 비용 |
| 근거성 | **환각 장소율**(DB에 없는 장소) | qwen3에서 실제로 관측된 실패 유형 |
| 제약 준수 | 지역·카테고리·슬롯 준수율 | 사용자 요구 충족 |

구현: `eval/trace.AgentTracer`(LangChain callback, 그래프 config로 전파), 검색·Maps는 타이머 래퍼(로직 불변).
